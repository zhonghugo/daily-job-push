# 「岗位机会」表字段规范（daily-job-push）

> 目标表由**使用者自己提供或新建**，token 存在 `~/.workbuddy/daily-job-push/target.json`，**不写在本文件里**（技能目录不含个人数据）。
> 本文件只规定**字段结构**，保证写入不报错。

## 表标识（运行时从配置读）

```bash
BASE=$(python3 -c "import json;print(json.load(open('$HOME/.workbuddy/daily-job-push/target.json'))['base_token'])")
TBL=$(python3 -c "import json;print(json.load(open('$HOME/.workbuddy/daily-job-push/target.json'))['table_id'])")
TABLE_URL=$(python3 -c "import json;print(json.load(open('$HOME/.workbuddy/daily-job-push/target.json'))['table_url'])")
```

没有 target.json → 走 `onboarding.md` 引导（用户已有表就取链接；没有就新建）。

## 字段清单（14 个；技能在"新入库"时写 11 个，另 2 个只在"归并老岗位"时更新，唯一人工专属字段是「投递反馈」）

| 字段 | 类型 | 技能写入 | 规范 |
|---|---|---|---|
| 岗位名称 | text | ✅ | 平台原始标题，不润色（保留薪资/年限后缀） |
| 公司名称 | text | ✅ | 简称去后缀（"XX科技有限公司"→"XX科技"） |
| 招聘链接 | text | ✅ | **去重键主来源，字段永不为空**。首选明细页 URL 原文（markdown 形式 `[查看岗位](url)`）；先按 SKILL 第 4 步补搜两轮，仍无则填「定位链接」（平台搜索页/公司职位列表页），备注写 `定位链接（<平台>搜索页）：明细页未获取…`。带跟踪参数的链接要清洗干净 |
| 薪资范围 | text | ✅ | 平台原文（`15-25K` / `2-4万`），换算后可加注释 |
| 工作地点 | text | ✅ | 城市+区域，页面没写就留空 |
| 来源平台 | select | ✅ | 白名单值：`BOSS直聘` / `猎聘` / `前程无忧` / `智联招聘` / `脉脉` / `公司官网` / `全职招聘网` / `企查查` / `自媒体` / `转载聚合` / `鱼泡直聘`（历史数据保留）。白名单**可扩展**：遇到新渠道先在 `references/platform-rules.md` 登记域名、在 `dedup_keys.py` 登记明细页特征、并在表内补该选项，然后使用 |
| 状态 | select | ✅ | **新记录一律 `待投递`**。人工流转值：`已投递` / `待跟进` / `不合适` / `已关闭`——技能不得改动这些状态 |
| 匹配理由 | text | ✅ | 一句话（≤30 字）：**简历 × JD 的交叉点**（有简历必按此写）；无简历退化为画像方向对照，摘要注明 |
| 备注 | text | ✅ | 抓取时间 + 搜索词，如 `2026-09-22 10:00 · "深圳 AI应用 招聘"` |
| 发布日期 | date | ✅ | 语义为"入表日前"（沿用本表惯例）——写运行当日；抓到页面真实发布日期时写真实值并在备注说明 |
| 岗位要点 | text | ✅ | **AI 提炼的 JD 要点**：职责 + 硬性要求，≤60 字；只写页面里有的内容，不编造。**必填**——JD 拿不到先补搜，仍无则写"未获取到 JD，仅标题线索"，不许留空、不许脑补 |
| 渠道数 | number（precision 0） | ⚠️ 仅归并时 | **这个岗位在几个平台被见到**（=「同岗来源」里**去重后的平台数**）。新入库写 1；同岗又出现在**新平台**时由 `dedup_keys.py` 归并 +1。**渠道数 ≥2 才是跨渠道在招信号**（实验 1 的核心指标）——同一平台重复见到（列表页+明细页、隔几天又搜到）只加来源行、**不加渠道数**，否则信号是假的 |
| 同岗来源 | text | ⚠️ 仅归并时 | **每个来源一行**（行数可能多于渠道数：同一平台两次见到就是两行），行内用 ` · ` 分段：`[首次见到] 平台 · 薪资原文 · 地点原文 · 裸URL`。新入库时写一行；归并时**追加**新来源那行，旧行一律不动——跨渠道/跨时间的薪资、地点差异因此被保留下来（这正是要看的信号） |
| 投递反馈 | text | ❌ | **唯一的人工专属字段**（用户手写投递结果），技能写入时一律留空 |

## 归并（去重命中老岗位时改什么）

`scripts/dedup_keys.py` 命中已有记录时，**只改「渠道数」「同岗来源」两个字段**，产出 `<out>.updates.json` 供 `+record-batch-update` 提交。

⚠️ **绝不改这几个字段**：`招聘链接`（它就是去重键本身，改了下一轮去重直接失效）、`来源平台`（只反映首次入库渠道）、`状态`（人工专属）、`薪资范围` / `工作地点`（老记录当时的原文，是比对基准）。

❗**存量表的链接键曾是废键**：早期记录把 `招聘链接` 存成 markdown `[查看岗位](url)`，而老脚本没脱这层壳，导致**链接去重对存量记录从未生效**（只剩「公司+岗位」兜底）。`dedup_keys.py` 已用 `raw_url()` 修好，但**表里可能已经躺着历史重复行**——脚本每轮装载后会跑一次**只读体检**把它们列全（见「去重键口径」第 4 条），清理由人做。


## lark-cli 常用命令

```bash
# 读（分页拉全量，ndjson 落盘）
lark-cli base +record-list --base-token $BASE --table-id $TBL \
  --page-size 200 --format ndjson --output existing.ndjson --as user

# 写单条也用批量命令（实测：当前 lark-cli 没有 +record-create）
#   select 字段传数组（如 "状态":["待投递"]），datetime 传 "YYYY-MM-DD HH:mm"
#   先写 1 条跑通，确认字段名无误再放量（字段名不匹配会整批失败）
lark-cli base +record-batch-create --base-token $BASE --table-id $TBL --as user \
  --json '{"create_records":[{ ...一条的字段... }]}'

# 批量写多条：同一命令，create_records 数组放多条，每批 ≤200 条、串行执行

# 归并回写（渠道数/同岗来源）：dedup_keys.py 已产出请求体，直接 @文件 提交
lark-cli base +record-batch-update --base-token $BASE --table-id $TBL --as user \
  --json @new_jobs.updates.json
#   返回只含 ignored_fields，不报错 ≠ 写进去了 → 必须回读核对

# 首次接入时补两个新字段（一次即可；缺字段时归并会整批写失败）
lark-cli base +field-create --base-token $BASE --table-id $TBL --as user --json '[
 {"name":"渠道数","type":"number","style":{"type":"plain","precision":0}},
 {"name":"同岗来源","type":"text"}]'

# 回读验证：重复 record-list，diff 新增条数与链接集合
```

写入前若不确定字段名，先 `lark-cli base +field-list --base-token $BASE --table-id $TBL --as user` 核对——**字段名不匹配会整批失败**。

## 去重键口径

1. **主键**：`招聘链接` 规范化——**先脱 markdown 壳**（`[查看岗位](url)` → `url`），再去 query/fragment/utm、小写 host、去尾斜杠。同页不同参数视为同一条
2. **退化键**：`规范(公司名称) + 规范(岗位名称)`——去空格/标点、去括号内容、小写。链接为空时**只能**靠它
3. **命中任一键 = 同一个岗位 → 归并（追加渠道），不再丢弃**；`scripts/dedup_keys.py` 已实现，勿在别处重写
4. **退化键去括号内容是有意为之**：同一岗位在 A 平台带 req id（`AI产品经理(J19661)`）、在 B 平台不带，靠这个才兜得住。代价是同公司同名不同岗共用一个键——所以候选命中退化键后，**逐行比括号限定词**（`paren_tokens`）：两边都有限定词且毫无交集 → 判定为两个岗位，该行不参与归并。
5. 边界情况要报出来给人看（脚本会打标，不要自己消化掉）：
   - `⚠️ 键冲突（本轮未归并）`：一条候选同时命中**多条**带 `record_id` 的已有记录（存量重复行，或候选不带限定词、看不出落哪条）→ **本轮不动**：不猜、不合并、不产生写回体，只报候选来源行 + 命中各行的记录 ID。等于这条候选本轮没落库，所以必须原样带给人
   - `❓ 同名不同限定`：退化键撞上、但括号限定词互斥（`(J19661)` vs `（HR领域）`）→ 按**新岗位入库**，并在报告里点名已有的同基础名岗位；若确为同岗请人工合并
   - `❓ 同名待确认`：候选带限定词而老行不带（或反过来）、只能靠公司+岗位名认定 → 两边限定词没有冲突证据，**照并但标注**（两个链接都留在「同岗来源」里），误合由人拆。两边都没有限定词时不算不确定，不报（否则每次跨渠道归并都报警，等于没报）
   - 存量体检（只读巡检，每轮都跑）：同一去重键下挂着多条**带 record_id** 的记录 → 报成清单
     - `⚠️ 同链接重复`：同一条 URL 多行、**岗位名一致** → 多半是重复行（历次重跑把公司名写飘了），人工合并；组内**状态不一致**时改打 `⚠️ 同链接重复但状态不同`——先定保留哪一份状态再合
     - `❗ 同链接但岗位名不同`：同一条 URL 下岗位名不一致 → **可能有行挂错了链接**，先核对再动
     - `❓ 同名待查`：退化键相同、链接不同 → 可能是几个真岗位，逐条判断；组内两两括号限定词互斥的（`(J19661)` / `（HR领域)` / `（数据运营方向）`）只是共用宽键的不同岗位，**不报**
   - ⚠️ 体检**只报不改**：不产生写回体、不动任何记录，清理由人做（技能**不得自动删行**）
   - 为什么需要体检：老脚本把 `招聘链接` 存成 markdown `[查看岗位](url)` 而没脱壳，链接去重对存量记录从未生效，表里已攒下重复行。清理有**功能性**理由：去重键下只要挂多行，命中该键的候选就整条不归并（走 `⚠️ 键冲突（本轮未归并）`），脏行会一直挡住跨渠道信号——不只是美观问题
   - 本地模式下体检静默：更正日志（`merges-*.ndjson`）里的同一岗位新旧版本本就没有 `record_id`，不算重复

## 谁写哪个字段（口径，勿混）

- **AI 写（新入库）**：岗位名称、公司名称、招聘链接、薪资范围、工作地点、来源平台、状态（一律「待投递」）、匹配理由、岗位要点、备注、发布日期，外加 `渠道数=1` 和一行 `同岗来源`
- **AI 写（仅归并）**：渠道数、同岗来源——命中老岗位时更新，其余字段一律不动
- **人写**：投递反馈（以及状态的后续流转：已投递 / 待跟进 / 不合适 / 已关闭）
- 「岗位要点」是 **AI 总结**，不是原文粘贴——提炼该 JD 最关键的职责与硬性要求，写给人快速判断用
